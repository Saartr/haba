## Коммиты и пуши — только по явной просьбе

Не делать `git commit` и `git push` автоматически после каждого изменения кода.

**Why:** Пользователь хочет контролировать когда и что коммитится. Автоматические коммиты на каждое изменение — лишний шум в истории и раздражает.

**How to apply:** Коммитить и пушить только когда пользователь явно просит («закоммить», «запушь», «сохрани в git»). При деплое через `deploy-backend.ps1` тоже не пушить автоматически — деплой работает через SSH pull, не через push.

Сообщения коммитов писать **по-русски**: заголовок и тело. Префиксы (`feat:`, `fix:`, `refactor:` и т.д.) оставлять на латинице — это конвенция. Пример:
```
feat: передача прав создателя группы

- habit/[id].tsx: шторка выбора участника, подтверждение, handleTransfer
- BottomSheet.tsx: children рендерятся только при visible=true
```

## Перед коммитом — проверить память

Перед `git commit` проверять, не устарела ли память (`.claude/memory/*.md`) из-за внесённых изменений, и обновлять её в том же или отдельном коммите.

**Why:** Память — источник правды для будущих сессий о текущем состоянии проекта (статусы фич, актуальные файлы/эндпоинты, принятые решения). Если код меняется, а память не обновляется, она быстро расходится с реальностью и начинает вводить в заблуждение (исторический пример: старый `project_arch_review_2026-06.md` и user-level дубликаты описывали уже удалённый Telegram Login Widget).

**How to apply:** После реализации фичи/фикса — пройтись по связанным файлам памяти ([[MEMORY]] как индекс) и обновить: статус («план» → «✅ реализовано»), изменившиеся пути/функции/эндпоинты, новые «How to apply»-правила. Не обязательно отдельным коммитом — можно вместе с кодом, главное не оставлять память неактуальной к моменту коммита.
