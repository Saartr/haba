## Статус: ждём макеты (2026-09-11), кода ещё нет

Пользователь попросил не планировать конкретику до макетов — модель данных, эндпоинты и поля
траты могут поменяться под экраны. Ниже зафиксированы только продуктовые решения.

Идея пользователя — «ежемесячные траты». Изначально звучало как учёт доходов/расходов с
категориями, историей и парсером банковских выписок. Переформулировано в **цель**, в духе
остального приложения: не бухгалтерия, а «не выйти за лимит».

**Why переформулировали:** ручной учёт трат — одно из самых бросаемых действий, а банковские
приложения уже сами раскладывают траты по категориям. Конкурировать с ними в «вести учёт»
тяжело. Сильный угол — группы: общий бюджет пары/семьи/соседей или челлендж.

## Решения пользователя

- **Цель — не выйти за лимит** за месяц
- **Соло и группа.** В группе **один общий лимит** на всех участников
- **Доходов нет** (пока)
- **В группе все видят названия и категории трат** друг друга
- **Парсер банковских выписок — отложен** до подтверждения, что фичей пользуются. Когда дойдёт:
  один банк, CSV/XLSX (не PDF), разбор на устройстве, хранить только итоговые операции —
  в выписках чужие персданные (ФИО получателей переводов, телефоны)

## Технические выводы (сверено с кодом)

- `habit_logs` **не подходит**: там одна строка на пользователя в день с одним числом
  (`UNIQUE(habit_id, user_id, date)`). Трат в день много, у каждой сумма/категория/название —
  нужна отдельная таблица
- **Деньги — в копейках целым числом** (BIGINT), не дробным
- На `checkin_type` в живой БД **нет CHECK-ограничения** (есть только `habits_type_check` на
  solo/group) — новое значение `'spending'` добавляется без миграции ограничений
- Тип отметки выбирается на шаге 2 мастера: `checkinTypes` в
  `app/(tabs)/custom-habit/step2.tsx` (сейчас `boolean` и `count`; `progression` скрыт)
- `computeHabitStatus` (`lib/habit-status.ts`) нужна новая ветка: «выполнено» = в пределах лимита
- Для пушей по записи уже есть `notifyEntryAdded` (`backend/src/push/notify.js`) — используется
  групповыми count-целями
- Фича **не зависит ни от пушей, ни от HealthKit** → на iOS работает сразу
- Валидацию суммы на сервере делать с первого дня: в [[backlog]] висит похожая дыра, где
  лидерборд групповой цели накручивается любым числом

## Черновик модели данных — ⚠️ НЕ решение, уточнится по макетам

```sql
habit_expenses — id, habit_id → habits ON DELETE CASCADE, user_id → users,
                 amount BIGINT NOT NULL CHECK (amount > 0),   -- копейки
                 category TEXT NOT NULL, title TEXT NOT NULL,
                 spent_on DATE NOT NULL DEFAULT CURRENT_DATE,
                 created_at TIMESTAMPTZ DEFAULT now()
                 INDEX (habit_id, spent_on)
habit_spending_limits — habit_id → habits, month DATE (1-е число), amount BIGINT
                 PK(habit_id, month)
```

Лимит хранится **по месяцам**, а не одной колонкой: иначе смена лимита в сентябре задним числом
перевернула бы вердикт «уложились ли в августе».

## Предположения — ⚠️ не согласованы, пересмотреть по макетам

- Только рубли
- Период — календарный месяц, сброс 1-го числа, неизрасходованный остаток **не переносится**
- Лимит можно поменять посреди месяца — действует на текущий месяц
- Дата траты — сегодня, можно выбрать другой день текущего месяца
- Превышение **разрешено** (реальную трату не запретишь): прогресс красный, маскот грустный
- Свою трату автор может править и удалять; создатель группы может удалить любую — как он уже
  может исключать участников
- История: текущий месяц по дням, прошлые месяцы доступны

## Ответы на уточняющие вопросы (2026-09-11)

- **Пушей нет** (пока)
- **Категории — фиксированный список + свои.** Любое введённое название добавляется в список
  категорий. Предполагалось: список своих категорий общий на цель (группу) — подтвердить по макетам

## Что важно не забыть при реализации (от макетов не зависит)

- **Удаление аккаунта** (`backend/src/api/auth.js`, транзакция в `DELETE /me`) явно перечисляет
  каждую таблицу со ссылкой на пользователя, а внешние ключи в проекте без `ON DELETE`. Любая
  новая таблица трат с `user_id` без правки этой транзакции уронит удаление аккаунта с `23503` —
  такой баг уже был
- Публичная страница `apptapa.ru/delete-account` перечисляет, какие данные удаляются вместе с
  аккаунтом (требование Google Play) — дописать туда траты, см. [[feature-legal-pages]]
- Месяц считать **по московскому времени**: сервер в UTC, трата в 00:30 1-го числа иначе уйдёт в
  прошлый месяц
- Своя категория через `ON CONFLICT (habit_id, lower(name))` — выражение обязано совпадать с
  индексом дословно, иначе `42P10` (та же ловушка, что была с partial-индексом Яндекса)
